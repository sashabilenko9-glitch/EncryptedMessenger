# EncryptedMessenger v2 — Roadmap

## Progress log

- **2026-09-25 — Key pinning (TOFU) blocks key substitution.** The real risk behind unauthenticated UDP discovery was not the spoofed packet itself but that the handshake trusted *any* key: a peer redirected to an attacker (via discovery, ARP spoofing or a wrong manual IP) encrypted its session key to the attacker's key. The old code even overwrote the stored key with the new one after warning once, so the attacker's key was silently trusted from the second connection on.
  - `MessengerClient`/`MessengerServer` take a `PeerKeyVerifier` delegate and call it right after the peer's KeyExchange — **before** a session key is sent/accepted. Mismatch → client throws `UntrustedPeerKeyException`, server hangs up without raising `ContactConnected`.
  - `ContactRepository.PinOrVerifyKeyAsync` does "pin on first use / else compare" as one atomic DB operation (no TOCTOU between two simultaneous first handshakes). Verification fails closed on errors.
  - The rejected key is held in memory (`_rejectedKeys`) and announced to the UI with its fingerprint (`KeyFingerprintPayload.Changed = true`, `ViaContactId` for manual contacts). `AcceptPeerKey` re-pins only if the pending key still has exactly the fingerprint the user saw, then reconnects. Losing `_rejectedKeys` on restart is safe: it only makes the app stricter.
  - UI: red banner under the chat header with the new fingerprint (selectable) and "Neuen Schlüssel akzeptieren" behind a confirmation dialog; sending is disabled while the key is untrusted.
  - Verified against a real `MessengerService` with a real and an impostor peer (same id, different keys): first contact pinned; inbound impostor's message never accepted and pinned key not overwritten; outbound connect to the impostor refused before it got a session key; warning routed to the manual contact's chat; accept with a wrong fingerprint ignored, with the right one re-pinned and connected. The WPF banner/dialog were not exercised by hand.
  - Deliberately not done: signing discovery packets (option A). With pinning in place a spoofed announcement can only cause a failed connect or a rename, and a signature alone wouldn't stop replaying a genuine packet from another IP.

- **2026-09-25 — Named-pipe access restricted; read receipts retried.**
  - **Pipe:** `PipeOptions.CurrentUserOnly` on both ends. Server: the pipe ACL now grants only the current Windows user (verified: a single `FullControl` entry for the user; Windows' default ACL gave Everyone read access to broadcasts containing plaintext messages). Client: .NET verifies the pipe's owner, so a pipe with our name created by another account ("pipe squatting") is refused and logged as a `SECURITY:` warning. Requires UI and service to run as the same user — already required by DPAPI.
  - **ReadAck retry:** new `MessageStatus.ReadAckPending` (stored as an int, so no schema change — `EnsureCreated()` can't alter existing tables). `MarkRead` records the owed receipt first, then tries to send it over the inbound connection from the sender or our outbound connection to them (never opening a connection just for receipts). `FlushPendingReadAcksAsync` retries on inbound connect, outbound connect and online transitions, oldest first, stopping at the first failure; a per-contact guard avoids parallel flushes. Flushes triggered while `_clientsLock` is held run un-awaited to avoid a self-deadlock (the semaphore isn't re-entrant). Verified end-to-end against a real `MessengerService` + pipe: sender offline → receipt stays `ReadAckPending` in the DB; sender reconnects → ReadAck arrives, status becomes `Read`; sender online → immediate receipt.

- **2026-09-25 — Presence, history and contact-list fixes (9 fixes).**
  1. **Inbound-only contacts are reachable:** `MessengerServer` now reports the peer's IP on `ContactConnected`; `ContactRepository.EnsureWithAddressAsync` creates the contact with that address, or fills in a missing one (a known address is never overwritten from an unauthenticated handshake). The peer's listening port isn't in the handshake, so the default port is assumed until discovery corrects it.
  2. **History shows the newest 50 messages** (was the oldest 50 — anything past message 50 disappeared on reopen); `skip` now pages further back.
  3–5. **Presence rewritten** around a new `PresenceTracker`: online = a live TCP connection (ref-counted, inbound + outbound) OR a discovery announcement within 3 broadcast intervals. A periodic sweep reports peers that went silent as offline; only real transitions are broadcast. Contact-list broadcasts now carry the current `IsOnline` flags, and the UI keeps unread badges, previews and the selection across refreshes. Discovery only writes to the DB when a contact is new or its name/address changed (LastSeen at most once a minute) instead of every 5 s per peer. The server no longer raises an unpaired `ContactDisconnected` for a handshake that failed halfway.
  6. **History is applied only to the chat it belongs to** (new `MessageHistoryPayload` carries the `ConversationId`).
  7. **Times are shown in local time** (`DateTimeToShortStringConverter` treats UTC/Unspecified as UTC).
  8. **Disconnect after a manual-contact merge is reported under the real id**, and only removes the client entry if it is still the same client.
  9. **`PipeServer` broadcasts are serialised**, so concurrent broadcasts can't interleave JSON lines.
  Also: a failed outbound connect/handshake now disposes its socket. Verified: 0 warnings/0 errors; a scratch harness passed 15 checks (newest-50 paging, discovery write suppression, address fill-in without overwrite, presence timeout and ref-counting, IP on inbound connect, no unpaired disconnect). The WPF UI flows were not exercised by hand.

- **2026-09-25 — Bug-fix pass after a full code review (8 fixes).**
  1. **Persistent identity:** `AppSettings.Load()` never saved on first run, so `UserId` was a fresh GUID on every start until the user pressed "Speichern" — conversation IDs changed, history vanished, peers accumulated duplicate contacts. Defaults are now saved immediately; a corrupt `settings.json` is kept as `settings.json.corrupt` instead of being silently discarded.
  2. **DPAPI migration no longer destroys keys:** any unprotect failure used to be treated as a legacy plaintext key and the file was overwritten — fatal for a `data/` folder copied to another user/PC or read by a service running as another account. Migration now only happens when the content really is a legacy key (`<RSAKeyValue>` XML / Base64 of 32 bytes); otherwise a clear `CryptographicException` is thrown and the file is left untouched.
  3. **No more process crashes from event handlers:** all `async void` handlers in `MessengerService` now go through a logging `RunHandler` wrapper (an escaping exception used to kill the service, or the whole UI in standalone mode).
  4. **Data paths anchored to the exe folder:** WPF and the service set the working directory to `AppContext.BaseDirectory` at startup (a Windows Service otherwise starts in `System32`).
  5. **End-to-end message IDs:** the service now reuses the UI's message ID, so delivery acks find the bubble (✓✓ used to appear only after reopening the chat); failures are reported back via a new `SendFailed` pipe message (✗).
  6. **Read receipts actually sent:** `MarkRead` now sends a `ReadAck` to the sender (`SendReadAckAsync` was never called); `DeliveryAckEventArgs.IsRead` distinguishes the two acks, and a new `MessageRead` pipe message turns ticks blue. Incoming messages received while a chat was closed are marked read when it opens. `MessengerServer` writes are serialised so acks from different threads can't interleave frames.
  7. **Per-connection session keys:** `CryptoManager` sessions were keyed by contact, shared by the inbound and outbound connection to the same peer — closing one deleted the key the other still used ("No AES session"). Each connection now has its own `sessionId`; the server also attributes messages to the handshake identity instead of the packet's self-declared `SenderId`.
  8. **Add-contact dialog closes on the first click** (WPF raises `Click` before `Command`, so the handler saw `Confirmed == false`).

  Verified: solution builds with 0 warnings/0 errors; a scratch harness against Core passed all checks (stable UserId, corrupt-settings backup, undecryptable key left byte-identical, legacy plaintext keys still migrate, two simultaneous connections in both directions, one surviving after the other closes, ReadAck arriving with `IsRead=true`). The WPF UI flows (5, 8, tick display) were not exercised by hand yet. **Protocol-level behaviour changed — update both peers.** Existing installs get one new (then stable) UserId on first start.
  All items from this review's list were fixed in the entries above (discovery spoofing is mitigated by key pinning: it can no longer lead to interception, only to a failed connect or a renamed contact).

- **2026-09-02 — P1.4 + P1.5 + P1.6 done: fingerprint verification, AES-GCM, DPAPI private key.** Rewrote `AesCryptoService` from AES-256-CBC to AES-256-GCM (authenticated encryption — tampering makes decryption throw `AuthenticationTagMismatchException` instead of silently returning corrupted data). This required fixing a related latent weakness: the old code reused one IV for every message in a session, which is merely discouraged under CBC but would be a critical break under GCM (nonce reuse leaks the authentication key) — `CryptoManager` now generates a fresh random 12-byte nonce per message/per storage-write and prepends it to the ciphertext+tag blob. The RSA session-key exchange payload shrank from 48 bytes (key+IV) to 32 (key only), since GCM doesn't need a pre-shared IV. Added `RsaCryptoService.ComputeFingerprint()` (SHA-256 of the public key, formatted as readable hex groups); `MessengerServer`/`MessengerClient` now surface the peer's public key through the handshake, `MessengerService.VerifyAndStorePeerKeyAsync()` persists it per-contact, detects and logs a `SECURITY:` warning if a contact's key ever changes from what was seen before, and broadcasts a new `KeyFingerprintPayload` over the pipe; the WPF chat header shows a fingerprint badge (tooltip = full fingerprint) plus a red "⚠ key changed" badge when `KeyChanged` is true. The RSA private key and the at-rest storage key are now DPAPI-protected (`CurrentUser` scope) via a new `DpapiProtectedFile` helper instead of plaintext files on disk. Added a transparent one-time migration: if DPAPI-unprotect fails on read, the file is treated as a legacy plaintext key, read as-is, and immediately re-saved protected — this was caught by testing against a real pre-change `data/` folder, which crashed with `CryptographicException` before the fallback was added. Verified live end-to-end: full RSA handshake + AES-GCM message round-trip between two real TCP endpoints, fingerprints matching on both sides, a flipped ciphertext byte correctly rejected, storage round-trip still correct, private key file confirmed non-XML on disk, and the full WPF app booting cleanly both fresh and against a legacy plaintext-key folder (migrates instead of crashing). Solution builds with 0 warnings, 0 errors. README's Security model section updated to match.
- **2026-09-02 — P1.3 done: self-contained/single-file publish.** Added a `Condition="'$(Configuration)'=='Release'"` PropertyGroup to `EncryptedMessenger.WPF.csproj` (`RuntimeIdentifier=win-x64`, `SelfContained=true`, `PublishSingleFile=true`, `IncludeNativeLibrariesForSelfExtract=true`, `PublishReadyToRun=true`) — scoped to Release only so day-to-day Debug builds stay fast and don't restore a runtime pack. Verified live: `dotnet build` (Debug) unaffected (same output path, no RID); `dotnet publish -c Release` produces one ~198 MB `EncryptedMessenger.exe` with no other required files; ran it from a folder with no project/SDK context and confirmed it starts, logs, and works standalone. Also confirmed a second launch correctly attaches as a UI-only client to the first instance's already-running service (existing pipe-detection logic) instead of conflicting on the TCP port. Documented the publish command in README.
- **2026-09-02 — P1.1 + P1.2 done: structured logging, silent-catch removal.** Added Serilog (rolling daily file sink under `./data/logs/`, wired via a shared `AppLogging.CreateLoggerFactory()` in Core) and threaded `ILogger` through `MessengerService`, `MessengerServer`, `MessengerClient`, `PeerDiscovery`, `PipeServer`, `PipeClient`, `MainViewModel`, `ChatViewModel`. All 36 `Debug.WriteLine` calls replaced with leveled, structured log calls. All 11 silent `catch { }` blocks now log the exception before continuing (1 exception: `AppSettings.Load()`'s fallback-to-defaults on a corrupt settings file is a deliberate, benign silent catch — left as-is). Fixed the long-standing CS4014 warning (unawaited `BroadcastAsync` in the `Disconnected` handler) as a side effect of making that handler `async`. Also added `data/` to `.gitignore` — it holds the private RSA key, the at-rest storage key, the SQLite DB, and now logs, none of which should ever be committed; this wasn't excluded before. Verified live: built and ran the standalone app, confirmed the log file is created and captures the full startup → discovery → handshake → pipe-connect sequence with correct levels. Solution builds with 0 warnings, 0 errors.

## Why

v1.0 is a working, end-to-end tested baseline: real RSA/AES handshake, working TCP messaging, peer discovery, persistent (now encrypted-at-rest) history. The point of v2 is not to rebuild it — it's to take it from "demonstrates the required technologies" to "holds up under actual scrutiny": errors are visible instead of silently swallowed, the crypto claims are backed by verifiable properties (key fingerprints, authenticated encryption), and the codebase is testable. That difference is what separates a checklist project from an engineering one, and it pays for itself the moment the project grows any new feature.

## Status check — already solid, don't redo

- P2P over TCP, hybrid RSA-2048 + AES-256 encryption, full async/await, WPF + MVVM, EF Core + SQLite.
- TCP length-prefixed framing is implemented correctly (`PacketHelper.cs`) — no fragmentation bug to fix.
- Message content is encrypted at rest with a persistent local key (fixed post-v1.0.0).

## Priority 1 — do these first

Grounded in actual counts from the codebase, not guesses:

1. ✅ **DONE — Structured logging.** 36 `Debug.WriteLine` calls across the network layer — all invisible outside an attached debugger, i.e. invisible in the self-contained `.exe` you actually hand out. Replaced with file-based logging (`ILogger<T>` via Serilog, daily rolling file under `./data/logs/`). Connection lifecycle, network errors, and crypto operation outcomes are logged (no sensitive data). See Progress log above.
2. ✅ **DONE (partially) — Remove silent `catch { }` blocks.** All 11 silent catches now log the exception. Not yet done: the custom exception types (`ConnectionFailedException`, `HandshakeException`, `DecryptionException`) and explicit network timeouts on every call — those are still open, worth a follow-up pass. User-facing feedback on failure already existed via ViewModel state (`IsConnecting`/`Status = Failed`) and is now paired with a log entry.
3. ✅ **DONE — Self-contained / single-file publish config.** `EncryptedMessenger.WPF.csproj` now has a Release-only `PublishSingleFile`/`SelfContained`/`RuntimeIdentifier=win-x64`/`IncludeNativeLibrariesForSelfExtract`/`PublishReadyToRun` block. `dotnet publish -c Release` produces one ~198 MB standalone `.exe`. See Progress log above. (The Windows Service project is left framework-dependent for now — it's an advanced/optional install path, not the "hand a friend one file" deliverable.)
4. ✅ **DONE — Peer key fingerprint verification.** SHA-256 fingerprint shown in the chat header (tooltip), computed on both sides after every handshake and compared against the previously stored key per contact; a mismatch logs a `SECURITY:` warning and shows a red "key changed" badge in the UI. Still manual (no QR yet — see ideas below) and doesn't block the connection on mismatch, only flags it.
5. ✅ **DONE — AES-GCM instead of AES-CBC.** `AesCryptoService` rewritten to AES-256-GCM; tampering now makes decryption throw instead of silently returning corrupted plaintext. Also fixed session-IV reuse (was safe-ish under CBC, would've been a critical break under GCM) by moving to a fresh nonce per message.
6. ✅ **DONE — Encrypt the RSA private key at rest.** Both the RSA private key and the at-rest storage key are now DPAPI-protected (`CurrentUser` scope) via `DpapiProtectedFile`, with a one-time transparent migration for files left over from before this change.
7. **Unit tests (xUnit).** Zero tests exist today. Cover: RSA/AES round-trip, packet serialization, `MessageRepository.ConversationId`, and an integration test of a full client↔server handshake + message on localhost. Do this once Priority 2's DI/interfaces land — it's much easier to test with mockable repositories.

## Priority 2 — valuable, not urgent

- **DI + interfaces** (`IMessageRepository`, `IContactRepository`, `ICryptoService`, `IMessengerService` via `Microsoft.Extensions.DependencyInjection`, one `ServiceCollection` shared between WPF and the Windows Service). Mainly valuable as groundwork for testing (P1.7) and for reconnect logic below — not an end in itself.
- **Auto-reconnect with exponential backoff, heartbeat/ping, outbound message retry queue.** Real robustness win for a flaky Wi-Fi LAN, but a meaningful chunk of new state-machine logic. Worth doing, not blocking.
- **Protocol versioning field** (`ProtocolVersion` in `NetworkPacket`, checked on handshake). Nearly free to add — do it while already touching the protocol for GCM/fingerprints (P1.4–5).
- **CI + polish:** `.editorconfig`, GitHub Actions (build + test on push), README architecture diagram, `docs/` protocol description. Cheap, good for a public repo, not functionally blocking.

## Explicitly skipped — and why

- **Migrating to SQLCipher (`sqlite-net-sqlcipher`) instead of EF Core + SQLite.** Would mean replacing the whole DB layer. The actual problem it solves (message content readable on disk) is already fixed with the app-level AES-at-rest key. The remaining gap — contact metadata (IP, display name) still stored in plaintext — is a minor exposure for a LAN-only threat model. Not worth the rewrite.
- **Avatars/`PersonPicture`, Away/DoNotDisturb/Sleeping presence states, custom `ScrollViewer` template, bouncing-dots typing animation, GIF sending (`WpfAnimatedGif`).** Pure UI polish. None of it strengthens correctness, security, or reliability — it's feature-surface, not depth. Worth doing only once Priority 1 is done, and only if visual richness is an actual goal (e.g. for a demo).
- **`TreatWarningsAsErrors` / `Nullable` as hard errors right now.** Good hygiene, bad timing — turning this on before the Priority 1 changes land just produces churn. Turn on once the code has settled.
- **A separate `IntegrityHash` (SHA-256) field on top of the packet.** Redundant once AES-GCM (P1.5) is in place — GCM's authentication tag already gives tamper detection. Doing both duplicates the same guarantee.
- **Perfect Forward Secrecy via ECDH.** Real cryptographic value, but a genuine handshake redesign — bigger and riskier than the fingerprint check it would sit next to. Defer until Priority 1/2 are done.

## Future ideas (not committed — brainstorm backlog)

- **Cross-platform client (MAUI or Avalonia) reusing `EncryptedMessenger.Core`.** The most promising idea here — `Core` has zero WPF dependencies. Not quite "as-is", though: it targets `net8.0-windows` and uses DPAPI for key protection, so key storage needs a platform abstraction (e.g. Keychain/Keystore) and the TFM must become plain `net8.0` first.
- **QR-code contact exchange.** Encodes `IP:port:fingerprint` for scanning — turns the manual fingerprint comparison (P1.4) into a one-tap UX and doubles as a security feature.
- **File / image transfer**, streamed through `CryptoStream`, using the existing typed-packet protocol.
- **Full-text search** over message history (SQLite FTS5) — cheap on top of the current EF Core/SQLite setup.
- **Encrypted backup export/import** — reuses the existing at-rest AES key.
- **Group chats.** The hard one: breaks the current "one AES session key per contact" model. Needs either pairwise per-member encryption (simple, doesn't scale) or a real group key with rotation on membership change (correct, non-trivial). Do this last, after Priority 1/2.
- **Optional relay/rendezvous server for off-LAN use.** Interesting (NAT traversal, hole punching), but works against the project's current "serverless" identity — keep as a maybe, not a priority.
